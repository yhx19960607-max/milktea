# 餐食识别模型方案

更新时间：2026-09-09 17:12

## 当前结论

- 当前云开发可用的免费模型 `hy3` 是文本模型，不能直接理解餐食照片。
- 当前控制台「生图模型」里的 `HY-Image` 系列用于生成图片或修改图片，不能用于识别餐食。
- 已实现的菜单照 OCR、识别结果微调、长文本菜单输入可以继续保留。
- 真正的「餐食照自动识别热量」需要多模态视觉模型，当前先暂缓接入。

## 分阶段方案

### 阶段一：免费可用版

| 输入方式 | 能力 | 状态 |
|---|---|---|
| 菜单照 | OCR 提取菜单文字，再交给 `hy3` 做结构化和热量补全 | 已具备基础能力 |
| 长文本 | 用户粘贴「食物,热量」清单，自动解析为可编辑列表 | 已具备 |
| 餐食照 | 先让用户确认食物名称、份量和热量 | 已具备 |
| 餐食照 | 模型直接看图识别菜品和热量 | 暂缓 |

### 阶段二：接入多模态模型

后续可接入支持图片理解的模型，例如：

- `glm-5v-turbo`
- 其他已上线且支持图片输入的多模态模型

> 2026-09-09 补充：控制台公告显示 `qwen3.5-flash`、`qwen3.5-plus` 将于 2026-09-08 下线；后续选型时应以云开发控制台的最新模型列表为准。

模型需要输出结构化结果：

```json
{
  "type": "food",
  "items": [
    {
      "name": "宫保鸡丁",
      "portion": "1份",
      "estimatedWeight": 250,
      "kcal": 320,
      "kcalRange": [280, 380],
      "confidence": 0.72,
      "ingredients": ["鸡肉", "花生", "辣椒"]
    }
  ]
}
```

低置信度结果必须进入用户确认页，不允许直接保存。

## 开源模型备选

| 用途 | 候选方案 | 备注 |
|---|---|---|
| 菜单文字识别 | PaddleOCR | 中文效果好，适合菜单照 |
| 餐食图片理解 | Qwen2.5-VL、InternVL3、MiniCPM-V | 需要云端部署和 GPU/CPU 算力 |
| 菜品/配料细分 | FoodSeg103、Food-101 | 对中餐和奶茶菜单覆盖有限，可能需要二次训练 |
| 热量估算 | 识别结果 + 食物库 + 用户微调 | 模型只能识别，热量必须依赖数据源 |

如果部署开源模型，建议用腾讯云 GPU 服务，把模型包装成 API，再接入云开发自定义模型。这个方案可控，但需要考虑服务器费用、并发能力和维护成本。

## 暂停原因与恢复条件

暂停原因：

- 当前免费模型不足以支持真正的餐食照片识别。
- 多模态模型需要额外费用或自建算力。
- 现有菜单 OCR + 长文本输入已能支撑第一版产品验证。

恢复条件：

1. 云开发出现可用的免费多模态模型。
2. 产品验证后确认用户强烈需要餐食照自动识别。
3. 愿意为此配置资源点套餐、标准版或云端 GPU。

## 下一步

- 继续保留菜单照 OCR、长文本输入和用户微调能力。
- 后续回到这个课题时，先确认云开发「生文模型」页面的最新可用模型。
- 如果要接多模态模型，优先用云函数调用，避免小程序端直接调用带来的基础库和密钥问题。
